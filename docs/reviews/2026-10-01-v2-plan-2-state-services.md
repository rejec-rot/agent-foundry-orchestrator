# 处理方案二：统一状态操作服务与运行上下文

日期：2026-10-01。依据：[复检报告](2026-10-01-v2-backend-recheck.md)。状态：处理方案，尚未实施。推荐采用本方案。

目标是在已经完成的模块拆分上，进一步收口跨进程协调、状态更新、审批恢复和目录传递。保留文件存储、独立 worker 和 Trusted Import 阶段，不引入常驻调度服务或新数据库。

## 核心边界

| 边界 | 负责的操作 | 对应问题 |
| --- | --- | --- |
| 统一运行上下文 | 启动时解析 tasks/locks/runtime/submissions，显式传给服务、adapter、CLI 和 checkpoint | Q4/Q5 |
| 共享互斥与租约基础 | 完整原子发布、短时更新互斥、owner token、续租和失锁处理 | Q2；为 Q1/Q6 提供基础 |
| 执行器状态服务 | 跨 worker 的槽位、节流、熔断读取与更新；检查实际 writer 生命周期 | Q1 |
| 任务与提交操作服务 | 创建/启动/恢复/审批/绑定/删除的受控读改写；保留版本、终态与幂等身份 | Q3/Q6/Q9 |
| 执行器调用与结果校验 | 先确定实际执行器再复核；每一次 reviewer 结果完整校验 | Q7/Q8 |

这些是职责边界，具体可以按现有模块组合，不要求为每个表格条目再建立一套框架。workflow 继续负责步骤推进，状态服务负责一致性与合法状态变更。

任务运行的长租约、元数据更新的短互斥、外部操作请求应分开。取消以持久请求送达运行边界，不能等整项任务执行结束才能取得运行锁。审批和删除则在对应状态操作的短锁内完成校验。

## 九项问题如何处理

| 问题 | 统一后的规则 |
| --- | --- |
| Q1 | 执行器 admission 在共享状态中原子取得槽位并检查最新熔断；所有熔断修改读取并合并当前状态，旧内存只用于展示或缓存 |
| Q2 | 所有持有者使用同一锁发布、恢复和释放协议，业务代码不自行拼装取锁流程 |
| Q3 | 旧 run、V2 start 和恢复入口调用任务操作服务；已有记录不能被定义加载重建，取消终态不可复活 |
| Q9 | 审批记录绑定 task、baseline、candidate/manifest 与授权范围；恢复入口验证签名和当前绑定后在新进程内重新生成可信审批 |
| Q4 | record/list/create 接收同一运行上下文，默认值只在入口解析一次 |
| Q5 | checkpoint 使用明确的上下文参数或受控桥接，等待与反馈更新采用同一 runtime；只传必要路径 |
| Q6 | 提交 key 的记录、绑定和删除全部进入同一个操作服务及互斥协议 |
| Q7 | author/fix 调用前先确定实际执行器和会话，再统一复核资格，记录实际运行身份 |
| Q8 | reviewer 首次及每次重试均调用相同的结果校验，校验取消、独立性、task/revision/run 绑定 |

文件原子写解决完整 JSON 的发布；短锁和版本/owner 校验解决并发更新。两者都需要，不能用 rename 替代读改写互斥。任何槽位或执行归属转移前，原 writer 的停止证据也必须满足当前安全要求。

## 实施里程碑

1. **基础协议**：补九项预期行为回归；统一运行上下文和锁发布，先关闭 Q2，确定各类状态文件的单一更新入口。
2. **跨进程护栏**：实现共享槽位、节流与熔断操作；两个以上独立 worker 的测试验证 Q1，覆盖崩溃回收与旧快照更新。
3. **操作入口**：旧 run/V2 start/审批/提交删除接入状态服务；完成 Q3/Q6/Q9，验证 CLI 批准后新 worker 可安全恢复。
4. **调用链贯通**：context 贯通提交及 checkpoint；统一 author/fix/reviewer 的实际对象与结果复核，完成 Q4/Q5/Q7/Q8。
5. **收尾验收**：相关及全量回归通过，扫描其他直接写持久状态的位置，逐一说明其允许的写入协议。

兼容 facade 可保留；其写操作必须委托统一服务，不能继续直接写任务真相。只做函数转发、继续各自保存状态，不能算完成本方案。

## 优点与代价

优点：直接解决本次暴露的共性原因——入口检查和实际写入/调用不一致、路径推导分散、多个进程各持状态快照。新增 Web/CLI 入口可以复用同一操作契约。能够承接现有模块拆分，迁移范围限于上下文和状态操作。

代价：修改范围比局部补丁大，需要迁移并核查全部相关写入调用方。共享服务若设计过宽，会增加理解成本，因此接口应围绕实际操作，避免建立通用插件化状态机。

相对工作量中等，适合继续长期维护目前的单机、多 worker V2 系统。不能据此宣称跨主机协调已经完成。

## 兼容与回滚

沿用 task ID、幂等 key、API 回执及现有证据格式的可兼容部分。旧记录缺字段时在受控写入处适配；缺少审批绑定证据时重新获得审批。

按里程碑切换调用方，迁移期间同一类状态只允许一种写入协议。回滚需考虑已写的新字段、互斥格式和在途租约，先停止派发并确认 writer 状态，再切回兼容路径。既有终态和熔断不能被覆盖。

## 验收标准

除九项复现回归外，必须包含真实多进程场景：并发 start、槽位上限、熔断更新合并、提交创建与删除竞争，以及跨进程审批恢复。另覆盖仓库外 cwd、自定义 runtime、失锁 writer、变更过期的审批及 reviewer 重试取消/碰撞。

验收完成后，应能从每个公开写入口追到统一状态操作服务；不会出现绕开该服务的普通 task/ledger/safety 写入。Trusted Import 的捕获、独立评审、授权、验收和最终 ref 更新复核继续保留。
