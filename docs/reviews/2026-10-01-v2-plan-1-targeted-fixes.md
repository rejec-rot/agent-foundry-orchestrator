# 处理方案一：在现有模块内补齐九项问题

日期：2026-10-01。依据：[复检报告](2026-10-01-v2-backend-recheck.md)。状态：处理方案，尚未实施。

目标是完整修复 Q1–Q9，保留当前文件存储、独立 worker、公开 API 和 Trusted Import 工作流。在现有职责所在模块内修改，减少本轮接口迁移。

## 具体改动

| 问题 | 处理方式 | 理由 |
| --- | --- | --- |
| Q1：跨进程护栏 | 在共享 runtime 下记录每个执行器的槽位、启动节流和熔断；短锁内重新读取、校验、合并、原子保存，禁止旧内存快照整文件覆盖 | 资格函数共用不能让各 worker 的 Map 自动一致 |
| Q2：锁初始化 | 先将完整锁内容写入临时文件，再以不覆盖方式发布；首次创建、续租、释放和回收使用同一互斥协议 | 外部读者不应见到尚未初始化的锁 |
| Q3：取消任务被重建 | 旧 run 在锁内读取持久记录；已有 ID 不重新初始化；取消终态拒绝启动，恢复走现有恢复入口，新任务使用新 ID | 保留取消证据和单调递增的 state_version |
| Q9：审批后仍无法启动 | 保存可验证且绑定本次变更的审批；start 在锁内核验后允许恢复，并向新进程内的 workflow 注入可信审批 provider | 修改 WAITING_HUMAN 判断本身不足以恢复授权链 |
| Q4：默认提交目录 | record/list/create 统一调用相同的数据根解析；显式目录覆盖保持支持 | 消除仓库外启动时出现的两份账本 |
| Q5：checkpoint 路径 | checkpoint CLI/API 增加受控 runtime 参数，提示中的命令携带它，父进程等待与反馈使用相同目录 | executorEnv 默认不传 AF_RUNTIME_DIR |
| Q6：并发 forget | 删除操作获取创建使用的同一提交 key 锁，在锁内重新读记录再决定删除 | 避免检查 PREPARED 后误删新绑定 |
| Q7：fix 原执行器 | fix 先按原会话确定实际执行器，再调用 selector 校验，最后记录 onRunStart 并 resume | 被校验和实际调用的执行器必须相同 |
| Q8：review 重试 | 首次与重试结果共用取消、session 独立性及结果绑定检查 | 第二次运行同样属于新的不可信结果 |

Q1 的槽位记录需要 owner token、worker/run 身份和租约。租约过期后先确认原执行 scope 停止，再释放容量；不能只减计数后立即让新执行器进入。锁和槽位都不能用普通覆盖写冒充首次独占发布。

## 实施顺序

1. 把九个探针场景转为预期正确行为的回归测试；增加真实独立子进程的并发测试，执行器使用本地 stub。
2. 修 Q2，再用可靠互斥修 Q1 的共享槽位、节流和熔断合并。
3. 修 Q3/Q9，验证旧 CLI 不能覆盖取消任务，以及审批跨进程恢复确实进入授权链。
4. 修 Q4/Q5/Q6，然后补齐 Q7/Q8。
5. 跑相关行为回归和全量测试，复检剩余生产写入入口。

每批都要通过行为验证后再进入下一批；运行任务不因本轮修复被隐式重新执行。

## 优点与代价

优点：修改集中在已确认的问题位置；维持现有接口和部署方式；可以按问题拆成较小的补丁，回归和回滚范围清晰。

代价：各模块仍分别组织持久状态操作。以后新增入口时，需要继续检查它是否使用正确的锁、context 和资格复核；维护上对跨模块测试的依赖较大。

相对工作量较小，适合当前急需修正运行行为、近期不准备调整状态服务边界的情况。这里的“较小”是与另外两套方案比较，不是工期承诺。

## 兼容与回滚

- 不删除旧任务、审批、账本或熔断记录。旧审批缺少必要的变更绑定时要求重新审批，不自动生成许可。
- 提交路径统一后，已知旧目录提供受控读取或显式迁移；同 key 冲突必须核对，不能直接覆盖或自动合并。
- 改槽位/锁格式前保留状态备份。回退必须先停止派发并处理在途 writer，确认格式兼容；不能通过删除熔断状态“恢复运行”。

## 验收标准

九项对应行为必须全部修正：全局限流有效、熔断不丢更新、取锁唯一、取消记录不变、批准后跨进程恢复、提交路径一致、checkpoint 能创建并等待反馈、绑定记录不被并发删除、fix/review 每次复核实际调用对象与结果。

需要特别覆盖：worker 崩溃、旧持有者失锁、写入失败、同 key 并发创建/删除、审批后变更过期、第二次 review 被取消或复用作者 session。现有测试通过不能替代这些新增边界验证。
