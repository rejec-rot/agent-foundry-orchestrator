# 权限域分离（Privilege Separation）

> 这份文档解释本系统**结构性最弱的一环**，以及它现在的真实状态。
> 所有数字与权限位都是在本机实测的，不是推断。

## 一、问题一句话

**控制面（control plane）的真源文件，是被它控制的东西（执行器）以同一个身份可写的。**

## 二、实测现状

```
$ id
uid=1000(reject) gid=1000(reject) 组=...,27(sudo),...,984(docker)

$ ls -l contracts/action-types.json config/executor-safety-profiles.json
-rw-rw-r-- 1 reject reject  734  contracts/action-types.json
-rw-rw-r-- 1 reject reject  392  config/executor-safety-profiles.json
```

执行器子进程由 `lib/adapters.mjs` 以 **同一个 uid 1000** 启动
（`execAsync` → `spawnManaged`，不切换用户）。

## 三、这导致什么（具体危害，不是理论）

一个执行器是 **带文件工具的 LLM CLI**。以同一身份运行时，它可以：

| 它可以做什么 | 后果 | 现有的"防护"是什么 |
|---|---|---|
| 改写 `tasks/<task_id>.json` 里的 `acceptance_cmd` | 让验收跑它想跑的命令 | 内容哈希锚定只在**下一次**运行时**检测到**（不阻止） |
| 改写 `contracts/action-types.json` | **把动作白名单改成自己的**，整个策略层失效 | 无（契约文件本身就是真源） |
| 改写 `config/executor-safety-profiles.json` | 改变"什么会让熔断打开" | 无 |
| 删除 `runtime/executor-safety-state.json` + `.initialized` | **清空熔断器**，把被封的执行器解禁 | 需要同时删两个文件（N2 修复），但它做得到 |
| 追加 `runtime/executor-runtime-events.jsonl` | 伪造审计证据 | 无 |
| 改写 `docs/`、`lib/` 自身 | 改掉规则本身 | 无 |

**为什么说这是"根因"**：项目里所有文件级防护都隐含一个前提——
**写者是配合的**。`executor-env.mjs` 不把安全状态文件的**路径**传给子进程，
那是"隐蔽性"而不是"权限"（默认路径是可猜的：`runtime/executor-safety-state.json`）。
在同一个身份域里再加更多守卫，收益递减：**"防护"退化成"事后检测"**。

这也是为什么 P3 的 SQLite 之争在方向上就偏了：**同一个 UID 拥有的数据库具有完全相同的性质。**

## 四、现在已经有什么（不要低估，也不要高估）

1. **环境变量指针隔离**（`lib/executor-env.mjs`）：不给子进程 `AF_SAFETY_STATE_FILE` 等指针。
   属于隐蔽性，不是权限。
2. **路径隔离（P2 沙箱）**——这是**目前在不提权前提下能做到的最强缓解**：
   容器里**只挂载工作区**，控制面文件不是"不可写"，而是**不存在**。
   实测：`planSandbox` 的 `applied.mountedPaths` 只有工作区，编排器根目录从不出现在 `-v` 里。
3. 但必须说清楚：`--user <uid>:<gid>` 传的是**宿主自己的 uid**，
   所以**身份没有分离**——它防的是"容器内以 root 跑"，不是"执行器变成另一个用户"。
   （`lib/sandbox.mjs` 顶部注释原先写成"breaks the root cause"，已改正。）

## 五、三个方案，以及本机能验证到哪一步

| 方案 | 做法 | 本机可行性 |
|---|---|---|
| **A. 专用 UID** | 建 `af-exec` 用户；控制面 root 所有、`0700`；工作区归 `af-exec`；编排器经特权路径写状态 | ❌ **无法验证**：`sudo -n` 不可用（组里有 sudo 但需要密码），`/proc/self/uid_map` 不可写 → 我无法建用户、无法 chown。**必须在部署时由有 root 的人完成** |
| **B. 每次执行一个容器** | 只挂工作区（已实现）+ 用**不同的容器 UID** | ⚠️ 部分可行：docker 可用；但工作区是宿主 bind mount（宿主 uid 所有），换成别的 UID 就写不进去 → 需要宿主上放宽权限（又要 root）或改用卷 |
| **C. 容器卷 + 受控回拷** | 工作区**拷贝进卷**，卷内所有权由容器自己决定 → 执行器以**真正的另一个 uid** 运行；产物经**校验器**拷回 | ✅ **本机可实现**（docker 可用，卷内所有权不需要宿主 root）。代价：每次执行要拷入拷出，且回拷必须经过校验（这是新的信任边界，必须显式设计） |

**我的判断**：如果目标是"真分离"，**C 是唯一在本机可完整实现并验证的路线**；
A 是理论最干净的，但必须在部署时做（我可以写好脚本与能力探测，无法在此验证）。
B 单独使用只是路径隔离（现状）。

## 六、能力探测（本机结果）

```
uid                 1000（非 root）
sudo -n             不可用
/proc/self/uid_map  不可写（无 user namespace）
docker              29.8.0 可用
bwrap / unshare     被拒（本会话早期实测）
systemd-run MemoryMax 不生效
```

含义：**A 与"用命名空间做隔离"在本机都做不了**；能做的只有基于 docker 的隔离（B/C）。
这份能力缺失是明确记录的，不做静默降级。

## 七、现状总结（一句话）

> 执行器与编排器**仍是同一个身份**；P2 沙箱把控制面从执行器的**视野**里移走了（路径隔离），
> 但没有把它从执行器的**权限**里移走。真正的分离需要一个第二 UID，
> 那需要在部署时用 root 完成（方案 A），或改用容器卷（方案 C，本机可验证）。
