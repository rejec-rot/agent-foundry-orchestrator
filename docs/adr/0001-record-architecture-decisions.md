# 0001 — 用 ADR 记录架构决策

- 状态：已采纳
- 日期：2026-09-16
- 决策者：本仓库维护者

## 背景

本仓库是 `agent-foundry-orchestrator` 的改造升级线。改造的核心动作是**用成熟组件替换手写实现**
（见 `docs/MODULE-MAP.md`），因此会产生大量"为什么换这个、为什么不换那个、取舍是什么"的决策。

上游项目已经有过一次教训：`lib/executor-runtime-guard.mjs` 的注释里写着
*"the old `runtime/executor-safety-policy.json` duplicate was removed because editing the wrong one
silently had no effect"* —— 说明**没有把决策写下来的代价，是后人会改错地方**。

## 决策

本仓库所有"引入/排除外部组件"与"架构性改动"都以 ADR 形式记录在 `docs/adr/`。

命名：`NNNN-短横线小写标题.md`，四位递增序号。

每份 ADR 必须包含：

1. **状态**：提议 / 已采纳 / 已弃用 / 被取代（被取代时写明取代者编号）
2. **背景**：要解决的问题与约束
3. **决策**：选了什么
4. **备选与为什么不选**：列出被考虑过的其它选项及排除理由
5. **后果**：正面与负面，包括引入的依赖、许可风险、可回退性
6. **验证方式**：怎么证明这个决策生效了（具体到测试名或命令）

## 必须开 ADR 的情形

- 引入任何第三方运行时依赖（本项目上游的既有原则是零运行时依赖，突破它必须记录）
- 替换/移除一个现有模块
- 决定某个"已知残留"是修还是有意不修
- 许可、发布、数据存储位置等非功能决策
- 任何会让 `docs/PRESERVE.md` 中性质失效的改动（**这类改动原则上应被拒绝**）

## 后果

- 正面：决策可追溯；新人/未来的自己能看懂"为什么不是看起来更简单的那种做法"
- 负面：每个阶段多一份文档开销
- 缓解：ADR 保持短小，一页以内

## 验证方式

`docs/adr/` 中存在 `0002` 及之后编号的 ADR，且每条被采纳的组件都能对应到一条 ADR。
