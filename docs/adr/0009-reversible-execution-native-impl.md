# 0009 — P7 可逆执行：借鉴 shepherd 的思路，自行实现（不引入其运行时）

- 状态：**已采纳**（自行实现，不采用 shepherd 运行时）
- 日期：2026-09-16
- 决策者：本仓库维护者（授权执行 V2 全计划）
- 相关：`docs/ROADMAP.md` §五 P7

## 背景

P7 是路线图中唯一的**可选**阶段，参考 `shepherd-agents/shepherd`（2.4k★, MIT）：
"把执行变成可逆的 Git-like trace，支持 observe / fork / **rollback**"。

与 P1–P6 不同，**这一项不是"替换"，而是"补一个缺失的能力"**——所以不存在"该不该换"的问题，
只有"用什么实现"的问题。

## 缺口是真实的

- `lib/recovery.mjs` 能从断点**继续**，但**没有任何东西能往回走**
- 实测：全仓 `grep -i "rollback|reset --hard|revert"` 在非测试代码中**零命中**
- 后果：一个 revision 通过评审却在验收阶段失败，或后续 revision 把工作区改得更糟时，
  **没有回到"上一个真的通过的状态"的路径**

（注意术语冲突：`lib/workbench.mjs` 里的 `checkpoint` 指**人工体验节点**，语义完全不同，
因此本模块刻意避开 "checkpoint" 一词，使用 **restore point**。）

## 决策

**自行实现** `lib/rollback.mjs`（git ref + plumbing），**不引入 shepherd 的运行时**。

理由与 P1–P6 一致：shepherd 是一套需要整体采用的运行时基底，而本仓库的原则 3 是零外部重依赖。
而它值得借鉴的是**思路**——"执行应当是可逆的 trace，而不是单向棘轮"。

## 设计与取舍（每条都有理由，且都落成了测试）

### 1. 捕获用 **plumbing 游离提交 + ref**，绝不移动 HEAD 或分支

```
git add -A → git write-tree → git commit-tree -p HEAD → git update-ref refs/af-restore/<task>/<rev>
```

捕获**不能干扰正在进行的工作**：HEAD、分支、reflog 全部不动，新的提交只通过 restore ref 可达
（RB-2 断言了这三点，包括"它不在任何分支上"）。

### 2. 恢复用 `git restore`，**不改写历史**

用 `git restore --source=<ref> --worktree --staged -- <捕获内的路径>`，而不是 `git reset --hard`
——后者会移动 HEAD/分支，等于替使用者改写历史。

**只还原捕获里存在的路径**，这一点是实测纠正的：`git restore -- .`（整个 pathspec）会**删除**
"现在有、捕获里没有"的文件，而安全留点里的 `add -A` 又把这些新文件变成了可被删除的已跟踪项。
按路径列表还原，才真正兑现"新增文件默认保留"的约定（RB-4）。

### 3. 恢复**本身也可恢复**——这是 shepherd 思路的真正落地

恢复前先给**当前状态**留一个安全点（`refs/af-restore/<task>/pre-restore-<ts>`）。
操作员因此**不必在"保留坏状态"和"丢掉产生它的工作"之间二选一**（RB-5 实测：可以把回滚再回滚回去）。

### 4. 删除是显式选择，且**只报告真正发生的删除**

`prune` 默认关闭。且实测发现：安全留点已把文件暂存，`git clean` 只删未跟踪文件 → **静默删不掉**。
因此改为「已跟踪用 `git rm -f`，未跟踪用 `git clean`」，并且**只有文件确实消失才计入 `pruned`**
（RB-4 断言 `pruned` 的内容，而不是只看返回值）。

### 5. 能力缺失必须显式（原则 5）

工作区不是 git 仓库时，捕获/恢复/能力查询一律返回 `NOT_A_GIT_REPO`
（RB-1 断言三种入口都拒绝），而不是"静默什么都没做"。

### 6. 自动留点是**可选**的，且拒绝会**记进任务**

验收通过时自动留点由 `AF_RESTORE_POINTS=on` 开启，**默认关闭**——因为捕获会把 git 索引同步到工作区状态，
在一个"并非编排器自己拥有的"工作区里这是可见副作用。开启后，若工作区不支持留点，
**拒绝原因会写入 `task.restore_points[]`**，不允许出现"看起来留了点其实没有"。

## 验证

```
RB-1  非 git 工作区：能力查询/捕获/恢复三处都显式拒绝
RB-2  捕获不移动 HEAD、不移动分支、新提交不在任何分支上
RB-3  恢复把被改坏的文件还原（核心性质）且 HEAD 不变
RB-4  捕获后新增的文件默认保留；prune 才删除，且 pruned 内容与实际一致
RB-5  恢复本身可逆（安全点可再恢复）
RB-6  不存在的留点 → NO_SUCH_RESTORE_POINT
RB-7  dry-run 不修改工作区、也不创建安全点
RB-8  按任务隔离列出留点
```

外加 CLI 冒烟：`af-admin restore-point capture|list|restore`，留点与回滚证据都落到任务文件
（任务即真源，不另建注册表），且写入时持有任务锁（与 P3 修复一致）。

`node --test`：263 通过 / 0 失败（原 255），零依赖。

## 后果

- 正面：补上了"回不去"的能力，且捕获/恢复都**不破坏**工作区历史或未提交的工作；回滚可回滚
- 正面：留点与回滚证据写入任务文件，可审计
- 负面：**捕获会把 git 索引同步到工作区状态**（`add -A`）——这是让快照包含任务新建文件所必需的，
  但确实改变了 `git status` 的观感。所以自动留点默认关闭
- 负面：`.gitignore` 忽略的文件**不进入**留点（`ls-files --others --exclude-standard` 语义）
- 负面：路径列表作为 argv 传递，超大工作区可能触及 argv 长度上限（未做分块）
- 负面：非 git 工作区**没有**可逆能力。要覆盖它需要另一套快照机制（tar/overlay），本轮**未做**，
  且不做静默降级——直接报 `NOT_A_GIT_REPO`

## 什么情况下应重新评估

1. 需要**非 git 工作区**的可逆能力（需引入快照机制，属新设计）
2. 需要跨任务/跨分支的 fork（shepherd 的 observe/fork 更完整）——那时整体采用 shepherd 才划算
3. 超大工作区使路径列表成为瓶颈
