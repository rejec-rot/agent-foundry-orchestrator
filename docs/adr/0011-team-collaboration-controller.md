# 0011 — 团队协作为核心，采用一个持租约的本地控制器

- 状态：已采纳；首期已在工作区实施，真实模型团队联调待验收。
- 日期：2026-10-01。
- 授权依据：用户明确目标为多 agents 协作平台，并选择[方案二](../design/MULTI-AGENT-PLAN-B-COLLABORATION-CORE.md)，随后要求继续实施。

## 决策

Team、Goal、Agent、WorkItem、Message、Artifact、Run 是协作对象。一个主作者规划工作依赖并整合成果，注册 worker 在独立物理投影中执行。CLI 与 Web 把操作写入耐久收件箱，一个常驻本地控制器持有 `team-controller` 租约，认领执行、路由消息、提交结果并作出交付交接。

这更新了历史 `FINAL_ARCHITECTURE.md` 的“零常驻守护进程”限制。数据库约束保持 [ADR 0005](0005-reject-sqlite-swap-fix-lock-coverage.md) 的既有决定；没有新增数据库、消息中间件或模型框架依赖。

团队生命周期的唯一真源是 `runtime/teams/<team-id>/journal/` 的不可变顺序日志，每个事件包含完整状态、前序摘要和序号。收件箱记录指令事实，CAS 记录内容事实，Web 读取投影。一个 Delivery 的生命周期仍在 `tasks/<id>.json`，由既有执行管理器持有任务锁；与团队的状态通过引用关联。

旧 scheduler 处理未绑定团队的历史任务。新的团队任务不得由旧 scheduler 派发、恢复或取消，旧 V2 的启动、消息与取消入口转交团队命令。交付服务执行评审、授权、验收和原子提升，不重新独立派发团队作者。

## 必须保留的约束

1. 成员身份与 CLI session/进程分开。路由复用全局能力、可用性、账号禁用和运行时护栏；保留独立评审执行器，所有写入成员不得与其重合。
2. 工作项、输入产物和每次 run 绑定目标版本、工作项版本及认领 token。人工调整使受影响节点和下游失效，无关产物保持；过期结果与回复不得进入新方向。
3. 执行器的强 writer scope 未确认清空时，不接受产物、不重跑、不交付。重启只接管已确认的范围；受信孤儿回收会先持久化证据再删除句柄，未知范围停在 `RECOVERY_REQUIRED`。
4. 人工指令采用操作 ID 去重和期望版本校验。`queued` 表示已持久化，`received` 表示已领取，`applied` 必须有关联的工作项版本或执行/产物证据。
5. 独立候选使用当前基线、不可变输入、全部成员的退出证据，经 Trusted Import 重新捕获、评审与授权。改变方向后旧候选失效；提升已经开始时拒绝在途方向变更，已完成目标的调整采用当前 canonical 创建新目标版本。
6. 共享执行器槽位与断路器状态跨进程串行提交；没有确认退出的托管槽位保留，晚到的限流反馈不能解除账号禁用。

## 生命周期与首期边界

`af-admin team serve` 可在前台运行；首次命令可启动同目录下的 detached 控制器，重复启动竞争由租约裁决。控制器收到 SIGINT/SIGTERM 停止派发、取消其控制的执行并等待退出；失去租约后拒绝新派发与状态提交。

首期默认一个主作者和三个 worker，支持配置 1–8 名 worker、最多 32 个工作项，并限制单目标运行次数和工作项尝试预算。消息通过下一次受控执行领取；不承诺模型调用在进程崩溃时恰好发生一次。跨目标共享成员、实时工具注入和日志压缩属于后续工作。

验证分开记录：确定性适配器证明控制协议及真实文件/Git 交付边界，本地 Chromium 证明页面与 HTTP 操作；真实模型账号、并发额度与部署隔离须另作团队验收。[实施记录](../reviews/2026-10-01-team-core-implementation.md) 列出实际结果。
