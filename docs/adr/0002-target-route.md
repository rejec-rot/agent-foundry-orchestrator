# 0002 — 改造路线选择：路线 1（保留架构，替换危险的手写件）

- 状态：**提议**（待维护者确认）
- 日期：2026-09-16
- 决策者：本仓库维护者

## 背景

`docs/MODULE-MAP.md` 给出三条路线：

| 路线 | 内容 | 改动面 |
|---|---|---|
| 1 | 保留 AFR 架构与业务语义，只把手写的高风险件换成成熟组件 | 中 |
| 2 | 持久化执行整体交给 conductor；AFR 只保留策略与角色语义 | 大 |
| 3 | 用 loopx / mission-control 直接替代控制平面 | 最大 |

约束：

- 上游是**零运行时依赖**的手写实现（~17k 行），基线测试 218 项全绿
- 已确立两个**不可替换**的设计资产（`docs/PRESERVE.md`）
- 尚未解决的上游许可问题（见 ADR-0003）意味着**不能公开派生仓库**
- 维护者目标尚未明确说明（学习/自用 vs 上生产 vs 开源）

## 决策（提议）

**采用路线 1**，按 `docs/ROADMAP.md` §五 的 P1–P6 顺序推进，每个阶段一个 commit。

选择理由：

1. **改动可回退**——逐模块替换，任一阶段失败只需回退该 commit，不像路线 2/3 那样一次性更换执行模型
2. **保住两个设计资产**——路线 1 不触碰 `acceptance.mjs` 的白名单+锚定，也不触碰路由器按能力而非角色排序的逻辑；路线 2/3 需要把它们"移植"进新引擎，移植即丢失风险
3. **优先消灭最高风险项**——P1（断路器）与 P2（沙箱）分别对应已证实的手写状态机缺陷（C5）与三个我做不到的残留（内存限额、孙进程逃逸、同 UID 根因），投入产出比最高
4. **许可风险最小**——只引入**组件**（库/工具）而非复制他人代码库，且可用 ADR 逐个评估许可

## 备选与为什么不选

| 备选 | 排除理由 |
|---|---|
| 路线 2（conductor） | 执行模型要从"任务循环"改为"JSON graph"，`executeTask` 重写；两个设计资产需要移植进 worker 策略，移植过程有丢失风险。**若目标变成"要上生产"，这条应重新评估**——它的可维护性长期更好 |
| 路线 3（loopx / mission-control） | 最省维护，但 AFR 的存在意义基本消失。**若目标只是"尽快拿到能用的多 agent 编排"，这条才是最优**——loopx 原生支持 DeepSeek Harness |
| 保持现状 + 只做安全修复 | 已完成的修复批次解决了最危险的三项（密钥外泄、孤儿进程、白名单绕过），但手写状态机与无内存上限仍在。**若目标纯为学习，这条是合理的** |
| 整体用 execa+OPA+SQLite 一次性重写 | 一次性大爆炸式替换会让 218 项测试同时失效，无法定位回归来源 |

**因此本 ADR 的成立前提是"维护者选择保留 AFR 架构"。** 若目标改变，本 ADR 应被标记为"被取代"。

## 后果

- 正面：风险可控、可回退、保住设计资产、优先消灭已证实的高危项
- 负面：**引入运行时依赖**，违背上游"零外部重依赖"原则。该原则本身没有对等品价值（它换来的是"什么都要自己写"，代价是把并发/状态机这类难题留给非专家实现），但突破它必须逐条记录理由与许可
- 负面：路线 1 不解决"长期可维护性"，若后续要上生产，仍可能回到路线 2

## 验证方式

- 每个阶段结束后 `node --test` 全绿，且通过数只增不减（当前 218）
- `docs/PRESERVE.md` 中列出的性质各有对应测试（INV-5、`acceptance-allowlist.test.mjs`、`executor-env.test.mjs`、`child-process.test.mjs`）
- 每个被采纳的组件在 `docs/adr/` 有独立 ADR，写明许可结论
