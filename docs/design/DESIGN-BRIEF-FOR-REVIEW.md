# 设计评审简报：AI 编码 agent 的写入范围约束与受信回拷

> 本文件是**交给外部评审者（另一个 AI 或人）的自包含简报**。读者没有本项目上下文，
> 因此先讲系统是什么、约束是什么，再讲难点与待决问题。
>
> 相关的项目内文档：`docs/PRIVILEGE-SEPARATION.md`（问题实测）、
> `docs/WRITE-SCOPE-ENFORCEMENT.md`（本文倾向的设计草案）、`docs/adr/0007`（孤儿回收）。

---

## 1. 系统是什么

**`agent-foundry-orchestrator`（AFR）** 是一个 **AI 编码 agent 的编排控制面**。它自己不写代码，
而是驱动多个 **AI 编码 CLI**（executor，如 `claude` / `codex` / `cline` / `command-code` / `dsh`）
去完成一个任务：

```
任务定义 → planner 出计划 → author 执行器改代码 → 独立 reviewer 评审
        → fix 循环（不通过就修）→ 验收命令（acceptance）→ 治理/发布
```

关键设计：

- **`ROLE != PLATFORM`**：同一个 CLI 可以在任务 A 当 author、任务 B 当 reviewer。角色是任务属性，
  不是平台属性。评审必须**独立于**作者（防"作者兼裁判"）。
- **两个刻意保留的自研资产**（主流框架没有对等品）：
  1. **验收命令静态白名单 + 内容哈希锚定**——执行前证明这条命令与创建时一致，防止命令本身被篡改；
     三点校验（执行前 / 重试前 / 加载时），跑过之后缺失或被改即判定为篡改。
  2. 上面的动态角色注入。
- **文件即真源**：`tasks/<id>.json` 是唯一生命周期真相，配原子写 + 每任务文件锁 + 崩溃恢复分类。
- **零外部依赖**：`package.json` 的 `dependencies` 为 `{}`。
- **熔断器永不自动自愈**：必须人工 probe→admit（按设计逆着常见断路器库的语义）。

## 2. 要解决的弱点（实测，非理论）

**执行器与编排器是同一个 Linux uid**（uid 1000）。因此控制面的真源文件对执行器**可写**：

| 文件 | 执行器能做 | 现有防护 |
|---|---|---|
| `tasks/<id>.json`（含 `acceptance_cmd`） | 改掉验收命令 | 哈希锚定只在**下一次**运行**检测到**，不阻止 |
| `contracts/action-types.json`（动作白名单真源） | 改成自己的白名单，策略层失效 | 无 |
| `config/executor-safety-profiles.json` | 改变"什么会让熔断打开" | 无 |
| `runtime/` 熔断状态 + 标记 | 同时删两个文件即可**清空熔断器**、解禁执行器 | 需要同时删两个（有缓解），但它做得到 |
| `runtime/executor-runtime-events.jsonl` | 伪造审计 | 无 |
| `lib/`、`docs/` | 改掉规则本身 | 无 |

已有一个基于 Docker 的沙箱，但它做的是**路径隔离**：容器里**只挂载工作区**，控制面文件
"不在视野里"，而不是"**没有权限**"。因此所有文件级防护退化成**事后检测**。

## 3. 运行环境约束（决定方案的可行性）

实测（本机）：

- 非 root；`sudo -n` **不可用**；`/proc/self/uid_map` **不可写**（非特权 user namespace 被禁）
- `bwrap` / `unshare` 失败；`systemd-run` 的 `MemoryMax` **不生效**；cgroup 无委派
- **Docker 可用**（本机唯一能用的隔离机制）

## 4. 核心难点

在"执行器和控制面同 uid"的前提下，两件事：

1. 如何**约束一个 AI 编码 agent 能写什么**；
2. 如何**安全地让它产出物回到受信域**。

两条候选路线：

- **方案 A（专用 UID）**：建 `af-exec` 用户；控制面 root 所有、`0700`；工作区归 `af-exec`；
  编排器经特权路径写状态。**需要 root，本机无法验证**，只能部署时做。
- **方案 C（容器卷 + 受控回拷）**：工作区**拷贝进 Docker 卷**，卷内所有权由容器自定 →
  执行器以**真正的另一个 uid** 运行；完成后产物**拷回**宿主工作区。本机**可完整实现**，
  但它引入了**一个新的信任边界**：回拷是"不受信 uid 的产物"重新进入"受信域"的**唯一通道**。

## 5. 我倾向的设计草案（可被推翻）

1. **写入范围声明（write set）**：planner 在计划期声明该任务允许写入的**目录/glob**，并**哈希锚定**
   （照抄验收命令锚定的做法：三点校验，跑过后缺失或被改 = 篡改）。粒度是**目录级**，
   不是逐文件——逐文件会把 agent 逼死，导致大量升级。
2. **四带漏斗**（目的：让绝大多数决定**走不到 verifier**）：
   - **A**：写落在声明内 → 机械放行，不打扰任何人
   - **B(i)**：命中**硬拒绝**清单（控制面路径；`realpath` 逃出工作区；`..`/绝对路径；符号链接；
     可执行位/setuid；超限）→ **确定性拒绝，永不上模型**
   - **B(ii)**：机械放行越界 → **刻意清空**（任何声明外的写都不自动放行）
   - **C**：其余一切越界写 → **独立 verifier** 裁决
   - **D**：控制面 / 提权 → 人工门
3. **拒绝必须是物理的**：工作区**只读**挂载，只有声明中的目录逐个 `rw` 挂入；
   越界写在文件系统层 `EROFS` 失败，而不是事后发现。（这条不依赖 uid 分离，今天就能做。）
4. **请求通道**：因为写不进去，执行器需要一条**可写但永不进工作区**的隔离区（如 `/af-requests/`）
   来表达"我想写 X、理由是 Y"；编排器**只收集、绝不应用**。
5. **verifier 不是 planner**：planner 是**申请者**不是**批准者**（否则就是"作者兼裁判"，
   且执行器输出会回流给它，构成注入通道）。scope verifier 只回答**范围问题**
   （"这个扩张是否被任务目标所必需"），**不判**"改动好不好"——后者是既有的独立
   content reviewer 的职责。两者**禁止合并**，合并=verifier 负载爆炸。
6. **批量裁决**：每 run 对整份越界清单**只裁一次**（不是逐次交互），输出结构化决策 + 证据。
7. **无合格独立 verifier 时 → fail-closed 到人工门**，绝不降级成作者自批。

## 6. 两个争论点（请独立判断）

**争论点 1：谁裁决"越界修改是否合法"？**
有人主张让 planner 顺手校准执行器的越界修改。我反对，理由是这违反项目自身的独立性原则
（计划生成者兼计划执法者 = 作者兼裁判，且执行器输出会喂回 planner，构成注入通道）。
我主张裁决必须是**机械规则 + 独立方 / 人工**。

**争论点 2：独立 verifier 会不会过载？**
对方担忧：(a) verifier 要裁决的东西太多、成瓶颈；(b) verifier 的模型智商要足够高。
我的回应：**负载是设计的结果，不是给定的**——把 A 带（声明内）与 B(i)（确定性拒绝）做大、
B(ii) 清空、C 带**批量成每 run 一次**，verifier 只剩"真正的范围扩张"这一小块，中档模型即可；
若一个问题非要"品味"才能判，说明它被错误地做成了内容评审。

## 7. 待决问题（请逐条回答）

1. **越界清单（`outside_manifest`）怎么获取才可信？** 执行器**自报不可信**；要可信就得靠容器侧 diff，
   而容器侧 diff 需要卷/overlay——等于把方案 C 的一部分提前。这是可行性关键：
   它决定**能否在"不改 uid、不做回拷"的前提下先落地写入范围约束**。
2. **一次范围批准应管一个 revision，还是管到任务结束？**（我倾向一个 revision，避免一次批准被无限复用。）
3. **是否有比"声明 + 锚定 + 漏斗 + 独立裁决"更简单、更不易被绕过的整体思路？**
4. **这个设计里哪一环最可能在实际使用中崩掉？**（agent 行为 / 成本 / 延迟 / 被绕过）
5. **B(i) 硬拒绝清单是否遗漏了重要项？**（当前：控制面路径、realpath 逃逸、`..`/绝对路径、
   符号链接、可执行位/setuid、超限）

## 8. 附：一个具体攻击样例（供讨论边界）

若"回拷"阶段不加策略地 `cp -a 卷/* → 宿主工作区`，一个带文件工具的执行器可以：

- 塞回一个 `tasks/TASK-X.json`（或指向它的符号链接）→ 覆盖任务真源、改掉 `acceptance_cmd`；
- 塞回指向 `/home/<user>/...` 的**符号链接** → 回拷时跟随链子写到工作区之外；
- 塞回带 `../` 的条目 → 目录穿越；
- 塞回 `.git/hooks/pre-commit`、可执行位、setuid → 在宿主侧被触发；
- 塞回海量/超大文件 → 撑爆磁盘。

因此"回拷时谁判断产物合法、按什么策略判"是本设计的核心，而不是附属细节。
