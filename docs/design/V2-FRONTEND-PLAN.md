# Agent Foundry Next V2 系统前端建设计划书

编制日期：2026-09-20。交付类型：实施计划，不代表前端或新增接口已经实现。

## 1. 结论与建设目标

前端定位为 **Trusted Import V2 任务工作台**。围绕一项任务，帮助用户定义目标与允许修改的范围、启动独立 author/reviewer 流程、查看密封候选差异和验收证据、确认正式代码版本的提升结果，并处理有明确恢复方案的异常。

首版完整闭环为：选择已配置项目 → 创建单任务 → 查看执行阶段 → 检查差异、评审和验收 → 查看正式版本及成果。异常处理以真实错误与控制面允许的操作为准。

页面主线是当前 V2 的候选代码交付流程。多步骤 DAG、完整人工审批、自动修复循环和运行中实时对话不作为首版承诺。旧版模块已经存在的功能，也须验证其与 V2 的连接后才能开放。

## 4. 信息架构与页面设计

### 4.1 导航

```text
任务工作台 /tasks
  新建任务 /tasks/new
  任务详情 /tasks/:id
项目 /projects
  项目详情 /projects/:id
执行器 /executors
运行环境 /environment
```

异常待处理集合放在任务首页，并可过滤；首版不建立缺少 V2 支撑的独立审批中心。任务的差异、证据和事件作为详情页标签，避免导航分散。

### 4.2 任务首页

首页提供“新建任务”、搜索和状态过滤。默认优先排列需要操作员查看的异常，其次是活跃任务，再是已完成任务。

每行显示目标摘要、项目、任务 ID、顶层状态、V2 当前阶段、author/reviewer、更新时间。行内只放服务端允许的操作。显示“数据更新于……”与断线状态。

顶部统计采用当前查询范围内的运行中、失败、完成数量。缺少结构化采集依据时，不显示百分比进度、剩余时间、token 或费用。

空态引导顺序：注册项目和验收配置 → 查看环境检查 → 新建任务。接口错误、无任务、筛选无结果分别呈现，不能统一显示“暂无数据”。

### 4.3 新建任务

采用三个连续区块；初次配置通过项目页完成，任务表单尽量只呈现与本次需求有关的选择。

| 区块 | 用户填写或选择 | 服务端生成或确认 |
|---|---|---|
| 目标 | 项目、goal、acceptance、red_lines、review_rules | 项目注册路径、配置版本 |
| 执行与范围 | author、reviewer、允许的模型配置、proposed_required、proposed_anticipated | 独立性、允许范围、执行环境及调用限制 |
| 验收与启动 | 选择受信验收 profile、查看任务摘要 | 白名单命令、acceptance_binding、资产身份、策略摘要、隔离目录 |

必须由控制面分配 candidate/CAS/materialize 路径。浏览器不能自由提交宿主路径、挂载配置、凭据、任意 shell 命令或自称可信的摘要。项目设置中的调用次数、时限和费用上限只有对应执行端已强制实现时才标为“已生效”；未实现的限制不能作为可依赖承诺。

预检区分静态检查与真实调用：静态预检验证字段、路径分离、canonical 基线、治理文件可读、执行器配置和 sandbox 条件；不会因打开页面自动运行模型。读基线时不得隐式执行 adoption。首次建立 canonical ref 属于显式启动或项目初始化操作，要在操作摘要中说明。

启动按钮显示“启动 V2 任务”。成功收到受理结果后跳转详情。重复点击或网络重试使用同一幂等键，不能产生两个任务。

### 4.4 任务详情：首版核心

```text
项目 / 任务 ID                     任务状态 · 当前阶段    操作菜单
目标摘要                           数据更新时间 / 连接状态

投影 → 编写 → 写者停止确认 → 捕获 → 评审 → 授权 → 验收 → 提升

概览 | 文件变更 | 评审与授权 | 验收证据 | 正式版本 | 事件
┌────────────────────────────────┬───────────────────┐
│ 当前标签页内容                  │ 项目与运行信息     │
│ 阻塞原因、实际产出或差异         │ author / reviewer │
│ 与当前任务版本对应的证据         │ 基线、候选摘要     │
│                                │ 隔离及写者证据     │
└────────────────────────────────┴───────────────────┘
```

概览直接回答当前做到哪里、是否失败、正式版本是否已经变化。author 完成只表示编写结束。reviewer PASS 只表示评审通过。只有控制面完成提升与最终记录后，显示任务完成。

文件变更页使用 manifest 和其对应的 projected baseline/candidate 快照；不对运行中的 candidate 做轮询 diff。捕获前显示“尚无密封差异”。文件列表呈现 ADD、MODIFY、DELETE、MODE 和统计，文本支持并排/统一差异，二进制和大文件显示元数据及受控下载入口。排除投影的文件不能显示成被删除。

评审与授权页显示 reviewer 结果、问题、required_changes、review_snapshot_digest，以及 authorization_closure 的实际结果。评审失败时优先读取顶层 `last_review` 等已留存记录，不能只依赖成功分支才写入的 `trusted_import.last_review`。授权不足显示原因，不模拟人工批准。

验收页显示 PASS/FAIL、tier、evidence_id、exitCode、stdout/stderr 摘要及快照、基线、命令绑定。证据有效性由服务端复核；浏览器不通过比较一个摘要就宣布“可信”。无结构化测试计数时仅显示退出码和输出，不编造通过数量。

正式版本页同时呈现本任务的提升提交与当前 canonical；后者可能被后续任务推进。区分“本任务已纳入正式历史”和“当前最新版本”。materialize_dir 未配置时显示“未配置成果物化”，不声称存在可打开的目录或网页。

事件页显示实际留存的执行记录和新增控制面事件。历史记录不完整时明确标注，不根据当前阶段倒推出历史完成时间。

### 4.5 项目、执行器与环境页

项目页：显示注册仓库、canonical ref/OID、受信策略、验收 profile、投影排除规则和物化策略。首版使用运维配置注册项目，浏览器以读取和选择为主；不提供任意目录浏览器或在线策略编辑器。

执行器页：分开呈现能力登记、登记可用性、运行时熔断、最近验证时间和来源。README 的成功组合可以标为“历史验证记录”，不能默认标为当前可用。配置模型与实际运行回传模型分开展示，不能把请求参数称为实际模型确认。AGY 的区域故障、认证问题和历史封禁记录不得混为一类。

环境页：显示 Node/Git、治理文件可读性、Docker/cgroup 条件、镜像配置和真实运行记录中的网络模式。cgroup writer scope 不等于文件系统隔离；host 网络不显示为断网。无检查记录时显示“未验证”。健康状态读取与探活动作分离，打开页面不触发外部模型调用。

### 4.6 视觉与交互规范

桌面优先，主工作区覆盖常见 1280–1920 宽度；窄屏先支持浏览任务和查看异常，复杂差异允许横向滚动。中文界面保留可复制的状态码、任务 ID 和摘要。

使用中性色背景、清晰表格和适度留白；蓝色表示执行中、琥珀色表示需处理、红色表示失败、绿色表示完成，同时提供文字和图标。摘要默认截短但可复制完整值，路径与代码使用等宽字体。首版优先键盘导航、可见焦点、对比度和错误定位。

## 5. 状态模型与异常语义

前端同时保留 `state` 和 `trusted_import.phase`；两者不能相互替代。以下阶段来自 `runTrustedImportTask`，中文为展示文案。

| 持久化 phase | 页面文案 | 注意事项 |
|---|---|---|
| 缺失 / CREATED | 待开始 | 不表示已经进入 V2 执行 |
| PROJECTED | 基线投影阶段 | 当前代码在实际投影前写入阶段，不能仅据此标记投影完成 |
| AUTHOR_RUNNING | 编写候选改动 | author 写 candidate |
| QUIESCE | 确认写者停止 | 需要 scope 证据，不能以进程退出替代 |
| CAPTURE | 捕获候选与计算差异 | 可能包含重基；当前没有单独持久化 REBASE 阶段 |
| REVIEW | 独立评审 | 评审密封快照；失败不会自动进入 V2 修复循环 |
| AUTHORIZATION | 验证修改范围 | 受信策略与累计授权闭包 |
| ACCEPTANCE | 隔离验收 | 结果和对应修订绑定 |
| PROMOTION | 提升与结果确认 | 可能已更新 ref 但尚未完成记录，需看事务证据 |
| PROMOTED | 已完成正式提升 | 正常完成同时具有 `state=COMPLETED` |

顶层 FAILED/CANCELLED 覆盖“仍在运行”的展示，但保留最后阶段定位问题。断开连接不是失败，超时未更新不是自动取消，promotion_intent 存在不是提升成功。

| 场景 | 页面应表达的事实 | 允许的下一步 |
|---|---|---|
| reviewer 非 PASS | 评审未通过及具体意见 | 查看问题；复制目标创建新任务，原任务证据保留 |
| 授权闭包未满足 | 哪些路径/动作不被当前范围接纳 | 查看证据；修改配置后创建新任务，或待未来审批集成 |
| 验收 FAIL | 本次验收失败；该失败发生在本次提升前 | 查看输出；按受信恢复方案或新任务处理 |
| REBASE_CONFLICT | 基线并发变化且同路径冲突 | 查看冲突，新任务或人工处理；不强制覆盖 |
| writer scope 未证实清空 | 无法安全捕获 | 检查回收证据，不能强行继续 |
| 提升后进程崩溃 | 正式版本结果待核验 | 服务端验证事务及祖先关系后给出恢复计划 |
| 取消 | 区分请求已受理、任务已取消、writer 已清理 | 根据实际清理结果显示残留与后续动作 |

“验收失败未提升”不能泛化成“所有 FAILED 都没有改动正式版本”；PROMOTION 阶段失败可能发生在 ref 已更新之后。

## 6. 实施前必须处理的接口与语义缺口

### G1：新增面向浏览器的服务边界

当前 `getTaskStatus` 仅返回 task_id/state/executor，不足以支撑 V2。新增白名单字段投影、分页、过滤、差异读取和证据读取。禁止将整份任务 JSON、环境变量或执行器配置直接返回浏览器。

### G2：专用 V2 提交与执行所有权

`submitTask` 默认 `withPlan=true`、`withIntentGate=true`，可能进入旧规划/审批路径。新增专用服务负责校验、受信配置解析、生成绑定、持久化并交给单一执行 owner；V2 不触发旧多步骤规划。

需复用/提取任务正规化与任务锁，不能直接从 HTTP handler 调 `executeTask` 后让请求寿命管理执行。运行 worker 与 Web 请求解耦，浏览器关闭后任务继续。启动、重连和进程重启必须读取已有任务，不重复启动 author。

### G3：统一 V2 恢复入口

静态核对发现：`classifyRecovery` 无 `TRUSTED_IMPORT_RUNNING` 专用分支；FAILED 被通用恢复分类为终态，`continueTask` 也拒绝终态；V2 测试则通过直接再次调用 `executeTask` 验证失败后重入和提升事务恢复。

因此“底层支持恢复”不等于现有 CLI recover 对所有 V2 场景可用。应新增 V2 恢复规划：结合 phase、author_completed、writer 证据、promotion_intent、当前 canonical 和锁，决定核验、继续或拒绝。执行前在锁内复核 state_version。严禁前端把 FAILED 改成运行状态来绕过限制。

### G4：核验取消与提升的竞争

现有取消处理覆盖运行状态与执行器句柄，但适配器的授权、验收和提升阶段没有统一的用户取消检查回调。不能将“取消 API 返回成功”解释为“本任务此后不可能提升”。

先定义并实现可取消边界：在受信阶段边界检查请求；与最终 ref 更新协调；ref 更新已发生时以实际事务为准并返回“已提交，无法撤销本次提升”。为各阶段补充竞争测试后再显示取消按钮。原子提交临界区之外的行为和 writer 清理也需明确，禁用按钮不能代替服务端拒绝。

### G5：结构化错误和可追溯阶段

`executeTask` 的通用异常分支保留 failure_reason 和执行错误分类，但未统一持久化 Trusted Import 的 err.code/details。新增错误字段并脱敏，保留原兼容字段；历史任务缺失代码时按原消息显示，不能从自然语言猜出精确错误码。

新增阶段事件用于时间线和耗时。事件属于展示/审计投影，生命周期仍由任务文件决定。任务更新和事件记录不一致时，以任务快照校准并标记事件缺口，不把事件流当第二调度器。

### G6：项目/验收 profile 与内容展示

新增项目注册、受信验收 profile 身份解析和目录分配。真实 profile 的内容及资产身份由控制面产生；测试中的示例摘要不能复制为生产配置。内容接口仅可读取任务对应快照中已登记的 blob，不提供任意 CAS digest 或宿主路径读取。

### G7：工作台协作的后续集成

现有 operator-control 在一次 run/resume 开始前收集消息，不是向当前运行中的 CLI 实时注入；“已接收”也不证明目标已经落实。体验节点需要与容器通信、V2 快照、author 重跑、调用预算和证据失效语义一起设计。未来接入时显示已排队/已被某 run 接收，只有另有证据才能显示已应用。

## 7. 技术结构与拟议 API

### 7.1 结构

```text
浏览器前端
  ↓ 同源 HTTP（首期快照轮询，后续可增加 SSE）
Web API：鉴权、输入校验、字段投影、幂等与动作计划
  ↓
V2 应用服务：创建 / 查询 / 恢复 / 取消协调
  ↓
唯一任务执行 owner → 现有 orchestrator / Trusted Import / adapters
  ↓
tasks JSON + locks + runtime 证据 + Trusted CAS + canonical Git
```

服务端沿用现有 Node.js ESM 环境。前端建议采用独立的 TypeScript 组件化应用；框架和具体依赖版本在实施时核对后锁定，不让选型阻塞数据契约。首版不迁移数据库，不另建工作流引擎。

拟新增目录：`web/`（页面与组件）、`server/`（HTTP 与投影）、`lib/v2-service/`（统一动作边界）、`tests/web-api/`（接口集成）、`tests/web-e2e/`（浏览器场景）。以上均是建议目录，本次未创建实现。

轮询起步建议详情活跃时约 2 秒、列表约 5 秒；不可见页面降频、终态降频、失败退避。它们是初始配置，须根据项目规模实测。state_version 用于任务快照排序；包含其他来源的组合响应另带观测时间或投影版本，不能把 task.state_version 当所有运维数据的版本。

### 7.2 接口草案

以下全部为待实现 HTTP 接口，不是当前仓库现有接口。

| 接口 | 作用 | 落地条件 |
|---|---|---|
| `GET /api/v2/capabilities` | 返回已实现页面动作、版本、功能开关 | 静态功能矩阵与运行条件分别呈现 |
| `GET /api/v2/projects` | 已注册项目与可选 profile | G6 |
| `GET /api/v2/projects/:id` | canonical、策略摘要、验收配置摘要 | 只读检查不得隐式 adoption |
| `POST /api/v2/tasks/preflight` | 校验拟提交任务 | G2/G6；不启动模型，不写正式 ref |
| `POST /api/v2/tasks` | 受理并启动任务，返回 202、task_id、operation_id | G2；幂等键、受信字段和执行 owner |
| `GET /api/v2/tasks` | 分页列表及筛选 | JSON 读取投影，排除模板，损坏记录独立报告 |
| `GET /api/v2/tasks/:id` | 状态、phase、版本、摘要及 allowed_actions | G1；允许动作由后端计算 |
| `GET /api/v2/tasks/:id/changes` | 密封差异清单 | 指定 snapshot_digest，分页 |
| `GET /api/v2/tasks/:id/file` | 对应快照内某路径的 old/new 内容 | 路径归一化、绑定快照、大小与类型限制 |
| `GET /api/v2/tasks/:id/evidence` | 评审、授权、验收、writer 与提升摘要 | G1；服务端复核有效性 |
| `GET /api/v2/tasks/:id/events` | 有界分页事件和运行记录 | G5；历史缺失明确返回 |
| `POST /api/v2/tasks/:id/recovery-plan` | 只读计算恢复计划及调用影响 | G3；返回计划 ID 和 state_version |
| `POST /api/v2/tasks/:id/recover` | 执行指定计划 | G3；锁内复核，不新增隐式调用授权 |
| `POST /api/v2/tasks/:id/cancel` | 提交取消请求并返回实际结果 | G4 完成后启用 |
| `GET /api/v2/operations/:id` | 查询长操作是否受理、执行、完成或失败 | 操作记录不取代任务生命周期 |
| `GET /api/v2/executors` | 能力、登记状态、熔断和证据时间 | 只读；不顺带探活 |
| `GET /api/v2/environment` | 已缓存的环境检查摘要 | 明确检查来源和时间 |

写接口带幂等键；针对已有任务的动作还带 expected_state_version。过期返回 409 和可读提示，界面刷新后重新计算动作，不自动复用旧恢复计划。400 为参数问题，403 为无权限动作，404 为资源不存在，422 为任务/策略不接纳，503 为服务暂不可用；HTTP 成功仅表示相应操作成功，不隐含任务 COMPLETED。

任务详情 DTO 至少包含：task_id、goal、project_id（新增映射）、state、phase、state_version、updated_at、author/reviewer 摘要、manifest.summary、评审/验收摘要、promotion 摘要、结构化 error、allowed_actions 和 observed_at。缺失字段返回 null 或明确 unavailable_reason，不构造成功默认值。

### 7.3 浏览器与控制面边界

本机部署默认绑定 loopback；提供会话鉴权及写请求来源校验。内网暴露需明确访问身份与传输保护。控制面 API 不能作为公开的无认证命令执行入口。

浏览器仅提交目标和允许选择的配置 ID，服务端重新校验。模型输出、日志、候选 Markdown/HTML 均按不受信内容渲染；首版不在控制面同源执行候选脚本。后续运行式预览使用隔离域和 sandbox，不能访问控制面会话。

查询与下载限制路径、类型、大小和分页；不暴露账号配置、密钥、任意环境变量或 Docker socket。现有运维 getter 可能投影冷却状态，需区分缓存读取与会写入状态的刷新逻辑，避免每次页面 GET 隐式改变运行状态。

## 9. 验收计划

先使用独立临时仓库和确定性 author/reviewer fixtures，覆盖真实 API 与浏览器；仅在需要部署边界验证时运行 Docker 用例。真实账号冒烟单独记录执行器、调用次数、时限、网络和费用范围，不能用模拟通过代替真实验证，也不把真实账号探活放入页面加载。

| 场景 | 必须满足的页面/系统行为 |
|---|---|
| V2 正常完成 | 详情跟随真实阶段；最后显示 COMPLETED/PROMOTED、提交 OID、有效证据 |
| 非法任务 | governed_write、多步骤、缺 reviewer、相同 author/reviewer 在启动前拒绝 |
| 配置不完整 | 缺强 writer scope、非法目录、未注册验收 profile 明确阻塞，不默认降级 |
| reviewer 失败 | 显示问题；不显示自动修复或已验收，不进入提升 |
| 授权不足 | 显示实际闭包原因，没有虚假的“人工批准即可继续” |
| 验收失败 | 显示 FAIL 和输出；验证本次验收失败未更新 canonical |
| 并发基线 | 无冲突重基后显示新快照和重新绑定证据；同路径冲突拒绝覆盖 |
| 提升后崩溃 | 按事务核验后完成；不重复 author、重复提升或伪造失败无改动 |
| canonical 后续推进 | 本任务提交与当前正式提交分别展示，并按祖先关系报告结果 |
| 取消竞争 | author/review/acceptance/promotion 各边界按定义返回；UI 不谎称 writer 已清空 |
| 过期恢复计划 | state_version 不匹配返回 409，旧页面不能执行过期动作 |
| 重复提交与刷新 | 同一幂等键得到同一结果；浏览器刷新、关闭不重启任务 |
| 服务重启 | 从任务真源恢复展示；不根据陈旧内存重复派发 |
| 内容展示 | MODE、二进制、大文件、缺失 blob、越界路径处理正确；脚本不执行 |
| 数据缺失 | 无 phase、无证据、旧任务、损坏文件、事件缺口显示真实未知状态 |
| 状态新鲜度 | 断线展示最后更新时间；历史执行器状态不冒充实时探活 |
| 回归 | 现有 V2、任务锁、取消、恢复、writer 终止相关测试通过；全量回归分别报告通过/失败/跳过/取消 |

首版完成条件：用户能够不编辑任务 JSON 完成一次受信 V2 任务；能从界面定位异常和查看对应证据；控制面只开放已验证的动作；界面不扩大原有写入权限，也不改变 canonical 的唯一提升路径。
